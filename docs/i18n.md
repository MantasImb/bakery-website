# Internationalization Guidance

Related docs:

- Decision: [`0006-use-next-intl-for-localization.md`](./adr/0006-use-next-intl-for-localization.md)
- SEO: [`seo.md`](./seo.md)

This document records practical localization rules for customer-facing V1 work. Keep durable trade-off decisions in the ADR; update this guide when implementation details or review checklists change.

## Scope

V1 localizes the customer ordering experience in Norwegian Bokmål and English.

- Supported customer locales are `no` and `en`.
- `no` means Norwegian Bokmål for V1.
- Norwegian Bokmål is the default locale.
- Admin and kitchen screens are not localized in V1 and use English UI copy.
- API routes are not localized.

## Routing

Customer-facing routes use explicit locale prefixes:

- `/no`
- `/en`

Use stable English path segments after the locale prefix, such as `/no/menu` and `/en/menu`. Translate visible navigation labels and page content, not route slugs, for V1.

The root path redirects deterministically to `/no`. Do not use browser-language negotiation in V1.

Unsupported locale prefixes, such as `/fr/menu`, should return not-found instead of redirecting to `/no`. Redirect only truly unprefixed customer routes to the Norwegian default.

Localized customer pages should live under the locale segment, for example `app/[locale]/(customer)/...`. Keep admin and API routes outside the locale tree.

Locale redirect handling should exclude framework internals, static assets, images, `/favicon.ico`, PostHog `/ingest` proxy paths, API routes, and admin routes. Locale redirects should target customer page routes only.

The customer language switcher should preserve the current stable path and swap only the locale prefix. The URL is the source of truth for the active customer locale.

Use clear language names in the customer switcher, such as `Norsk` and `English`, rather than compact codes like `NO` and `EN`.

Show the language switcher during checkout, but keep it unobtrusive. If a customer switches language during checkout, preserve cart and entered data where technically feasible and only change UI language. Capture the order/email locale from the final checkout or order route at submission time.

Cart, checkout, payment return, and order confirmation routes should preserve the active locale unless the customer explicitly switches language.

Cart and checkout should stay locale-prefixed for customer clarity, even if their SEO metadata marks them non-indexable.

Order confirmation should also remain locale-prefixed for language continuity, but it is customer-specific and should be non-indexable.

## next-intl

Install and wire `next-intl` directly in the internationalization skeleton. Do not build temporary hand-rolled dictionaries first.

Use `next-intl` for:

- localized customer routes and navigation;
- customer-facing UI messages;
- validation, empty-state, loading, not-found, and recoverable-error messages;
- customer transactional message copy when that feature is implemented;
- customer-facing formatting where `next-intl` provides the right primitive.

Do not write full transactional email templates during the initial internationalization skeleton. Prepare locale capture and message structure, but implement actual email copy when notification workflows exist.

Keep `next-intl` usage direct where practical. Add project-owned wrappers only after repeated product code proves they are needed.

Keep supported locales, default locale, and narrow route helpers in one small i18n/routing module used by `next-intl`, proxy, metadata, the language switcher, and tests.

Define a shared `Locale` type from the supported locale constants. Reuse it for route params, message loading, checkout/order locale capture, analytics properties, and Sentry context where appropriate.

Use `next-intl` navigation helpers directly at first. Add a local localized `Link` wrapper only if repeated usage or design-system integration proves it is useful.

Validate locale at route/request boundaries and when persisting checkout or order locale. Keep domain modules locale-agnostic unless locale is part of the business rule, such as requiring localized product content for every supported customer language before weekly menu publication.

## Messages

Customer-facing message keys must exist in both `no` and `en`. Missing translations should fail tests or build checks instead of falling back at runtime.

## Customer Copy Tone

Customer-facing Norwegian and English copy should be clear, warm, and direct. Favor simple wording that works for older customers and families.

Avoid clever or playful wording in validation, checkout, payment, pickup, allergy, allergen, dietary, cancellation, refund, and error copy. These areas should prioritize clarity and confidence over brand voice.

A full translation glossary can wait until real product content exists, but important customer instructions should stay consistent across both languages.

The initial localized homepage copy can be clean placeholder-quality copy for proving the i18n system and tone. Final sales and product copy should wait until the active weekly menu and product content model exists.

Use shallow nested JSON message files by surface or shared namespace:

- page or workflow copy belongs under the owning surface;
- exact phrases reused across customer-facing surfaces may live in a shared namespace;
- avoid one large flat message file.

Initial message files should live at the repository root under `messages/no.json` and `messages/en.json`. Keep the files centralized until app size or translation workflow proves that splitting them is worth the overhead.

V1 should use message-key parity checks and route smoke tests. Defer generated message-key types until key mistakes become a recurring source of defects.

## Customer Content

Keep localized UI messages separate from persisted product content.

Product-facing text content must exist in both supported customer languages before a weekly menu can be published. Do not silently fall back between Norwegian and English product content.

Product images are locale-neutral and should not contain language-specific text.

Admin product editing should make both required customer-language content sets visible in one workflow. The exact layout can be side-by-side or stacked sections depending on visual fit, but V1 should avoid hiding required translations in a way that makes missing content easy to miss.

Allergen and dietary information is safety-sensitive. When product content is implemented, use consistent localized labels or a controlled vocabulary for allergen/dietary notes instead of relying only on free-form phrases. Product descriptions can stay free-form.

Admin order detail views should show the customer's captured locale as small operational metadata when email or support behavior depends on it. Do not make customer locale prominent in kitchen production views unless it helps support communication.

Localized product slugs are deferred. If product detail pages are added later, start with stable product IDs or stable non-localized slugs, and revisit localized slugs only if product discovery or SEO requirements justify it.

User-provided checkout data, such as names, email addresses, phone numbers, and notes, should never be translated. Store it as provided or normalized structurally, and localize only surrounding labels, helper text, validation, and errors.

## Formatting

Use the active customer locale for customer-facing money, dates, times, and numbers.

- NOK is the only V1 currency.
- Persist money, dates, and pickup windows as structured values, not localized strings.
- Use explicit localized pickup labels instead of ambiguous numeric-only dates.

## Checkout, Stripe, And Email

Cart data stays locale-neutral.

Checkout or order state should capture the customer locale when needed for transactional emails and later customer communication.

Customer transactional emails use the locale captured from the checkout or order route. Do not infer email language later from browser headers or admin UI state.

After order creation, keep the order's customer locale fixed for transactional communication such as confirmations, reminders, cancellations, and refunds. If a customer manually opens an order confirmation route in another locale, the page UI may render in that route locale, but email language should remain the captured order locale.

If admin resend actions are added, customer emails should resend in the original order locale only for V1. Do not add manual resend-language selection unless support workflows prove it is needed.

Pass customer locale to Stripe Checkout where supported, using a minimal project-locale to Stripe-locale mapping. Locale-prefixed success and cancel return URLs remain the source of truth for post-payment site language.

## Metadata

Customer-facing metadata should be localized and include practical alternate links for `/no` and `/en`.

Localized pages should use self-canonical URLs. For example, `/no/menu` canonicalizes to `/no/menu`, and `/en/menu` canonicalizes to `/en/menu`.

Use `hreflang` alternates to connect localized variants. Include `no`, `en`, and `x-default` where practical. `x-default` should point directly to `/no`, not `/`, because `/` is only a deterministic redirect.

When sitemap generation exists, include both localized canonical customer URLs and alternate language metadata where supported. Do not include unprefixed customer URLs such as `/menu`.

Keep the SEO metadata pattern lightweight but centralized enough that richer metadata can be added later without rewriting every page.

## Observability And Analytics

Customer-facing analytics events keep stable English event names and include a safe `locale` property for segmentation.

Customer-facing Sentry context may include the safe `locale` value when available. Do not send translated messages, request bodies, customer contact fields, or full provider payloads to Sentry.

## Testing

Tests should combine:

- message-key parity checks for both supported locales;
- representative customer route smoke assertions for high-value visible strings in `no` and `en`;
- behavior tests that avoid depending on every exact translation.

Include localized validation, empty-state, loading, not-found, and recoverable-error messages in coverage.
